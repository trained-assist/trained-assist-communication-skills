# trained-assist-communication-skills

Общий state-first контур для диалогов: извлечение состояния, формулирование следующей открытой цели и генерация сообщения. Отдельный resolver выбирает из закрытого списка там, где этого требует вызывающая сторона. Первый потребитель — рекрутинг; далее sales и другие домены.

**Рантайм: Cloudflare Worker** (VM на GCP выводится из эксплуатации — agent#2053, решение владельца 03.10.2026). Методы не зависят от VM: ни файлов, ни процессов, ни локальных секретов. Модель — через общий `trained-assist-llm-ladder`, который сам является Worker'ом, поэтому путь запроса Worker→Worker.

Контракты: [docs/spec.md](docs/spec.md) (writer) · [docs/extract-conversation-state-contract.md](docs/extract-conversation-state-contract.md) (state) · [docs/evaluate-next-goal-contract.md](docs/evaluate-next-goal-contract.md) (goal) · [docs/resolve-user-intent-contract.md](docs/resolve-user-intent-contract.md) (resolver) · ТЗ: [#6](https://github.com/trained-assist/trained-assist-communication-skills/issues/6), [#10](https://github.com/trained-assist/trained-assist-communication-skills/issues/10) и эпик #11

## Инструменты MCP

### `generate_next_message_to_conversation_partner` (contract v1)

Пишет ОДНО следующее сообщение по явно заданной цели. Не выбирает шаг процесса, не отправляет. Возвращает черновик.

Что делает сверх простого «напиши сообщение»:

- **Состояние диалога** (`src/dialog-state.mjs`) — извлекается из ПОЛНОЙ истории детерминированно, без вызова модели: отвеченные вопросы, отказы, незакрытые вопросы собеседника, обещания, условия. Каждый факт — дословная цитата с id сообщения, поэтому отрицание не теряется («офис не рассматриваю» не превращается в «рассматриваю офис»).
- **Запрет контакта** → `no_message_needed`, модель НЕ вызывается. Это решение, а не подсказка в промпте.
- **Guard** — детерминированный, не тратит модель: ограничения, повтор, переспрос решённого вопроса, выдуманное время. При отклонении — повтор с объяснением, ЧТО не так (иначе модель повторяет ту же ошибку и бюджет сгорает впустую). Общий retry budget = 2 попытки всего.

### `extract_conversation_state` (contract v1)

Извлекает структурированное состояние из полной истории по переданной `state_schema`. Не выбирает следующую цель, не пишет сообщение и не отправляет ничего.

- **Ограниченный schema subset.** Поддерживаются только простые JSON Schema-подобные поля (`type`, `properties`, `required`, `additionalProperties:false`, `items`, `enum`, min/max bounds, `description`). Unsupported schema падает до вызова модели.
- **Строгий JSON после модели.** Provider `response_format` используется, но не считается гарантией: ответ парсится и валидируется локально; одна ремонтная попытка, затем `STATE_REJECTED`.
- **Без раннего сжатия в MVP.** История передаётся целиком; превышение бюджета даёт `INPUT_TOO_LARGE` с размерами.
- **Свежесть.** `conversation_revision` возвращается в теле и диагностике. Если за время вызова пришло новое сообщение, потребитель обязан отбросить старый результат.

### `evaluate_next_goal` (contract v1)

Формулирует открытую следующую цель по верхнеуровневой цели диалога и state. Например: «уточнить, с какими CRM кандидат работал и какие задачи в них выполнял».

- `reason` необязателен; пустое значение допустимо.
- `wait`, `no_matching_option` и явный запрет контакта возвращают `goal:null`; потребитель останавливается до writer.
- Ревизия диалога возвращается в ответе для отбрасывания устаревшего результата.
- `resolve_user_intent` остаётся отдельным методом для задач, где вызывающая сторона действительно передаёт закрытый список решений.

### `resolve_user_intent` (contract v1)

Формулирует цель пользователя и выбирает **ровно один** id из закрытого списка, который передала вызывающая сторона. Не исполняет решение.

```json
{ "user_goal": "Подобрать актуальные вакансии по резюме, не отправляя отклики", "decision": "start_opencode" }
```

Встроенного списка маршрутов нет: `quick_llm_reply` и `start_opencode` — конфигурация потребителя, а не enum метода. Замена списка меняет разрешённые id без изменения кода.

- **Ровно два поля.** Ни `route`, ни `confidence`, ни `reason` в публичном JSON; диагностика — в `_meta` (MCP) и в заголовках (REST), включая версию пакета, по которой вызывающая сторона отсекает устаревший результат.
- **Динамическая схема на каждый запрос**: `decision.enum` = переданные id + `no_matching_option`, оба поля required, `additionalProperties: false` — и серверная валидация после вызова даже с provider JSON Schema.
- **Guard, 0 токенов**: цель не повторяет описание варианта (иначе это формулировка возможности приложения, а не желание пользователя), нет выдуманного времени, нет утверждений о содержимом непрочитанного файла. Одна ремонтная попытка с причиной; бюджет метода — 2 вызова лестницы.
- **Манифест ≠ содержимое.** Вложение без переданного текста помечается в промпте как непрочитанное; содержимое по имени файла не выдумывается.
- **Сжатие длинного ввода** (`src/intent-compress.mjs`) — детерминированное, без модели: событие длиннее 12000 символов сводится к первому и последнему предложению плюс тем, что несёт команду, отрицание, условие, факт или ссылку на источник. Порядок жертв — по цене ошибки: `fact → question → source → command → negation`. Отчёт `input_compressed` в `_meta`.
- **Ни одного вызова наружу, кроме общей лестницы.** `resource_ref` не открывается, чужой tenant недостижим by construction, «VM выключены» к методу отношения не имеет.

## Эндпоинты

| Путь | Что |
|---|---|
| `GET /health` | публичный, без токена; честно сообщает `not_configured`, если нет ladder-конфига |
| `POST /mcp` | MCP streamable HTTP (`initialize` / `tools/list` / `tools/call`) |
| `POST /v1/dialogs/next-message` | writer по REST (issue #6 §1) |
| `POST /v1/conversations/state/extract` | state extractor по REST (epic #11) |
| `POST /v1/conversations/next-goal` | выбор следующей цели по state (epic #11) |
| `POST /v1/intents/resolve` | resolver по REST (issue #10 §1) |

Все, кроме `/health`, требуют `Authorization: Bearer <COMMUNICATION_TOKEN>`.

## Запуск и проверка

```bash
npm ci
npm run gate          # check + 272 юнит-теста + песочница 35/35
npm run corpus        # 100 размеченных кейсов resolver'а, офлайн
npm run corpus:live   # те же кейсы против живой лестницы (нужны её секреты)
npm run corpus:live -- --catalog integration-v1   # приёмка вызова control plane: 25 кейсов на его каталоге решений
npm run dev           # wrangler dev на :8787
```

Песочница — замкнутый цикл без сети и модели: фейковая лестница по реальному HTTP-контракту, настоящий MCP `tools/call`. Она проверяет не только ответ, но и **что реально дошло до модели** (`prompt_contains`, `response_format_json_schema`) — иначе состояние диалога можно было бы выкинуть и остаться зелёными.

Размеченный корпус resolver'а (`scripts/corpus/cases.json`, 100 кейсов на шести разных каталогах решений) прогоняется в двух режимах. Офлайн-лестница подменена скриптом: это проверяет контракт, самосогласованность меток и то, что guard ловит поданные ему дефекты — но **не** доказывает, что модель выбирает правильно. Замер качества — только `corpus:live`, и раннер печатает это предупреждение сам.

## Границы

- Нет HH tokens и HH API; выбор шага, ATS, хранение черновика, preview и отправка — у потребителя.
- Своя лестница моделей запрещена (ADR-0001): только общий `llm-ladder`. Writer ходит в `conversation`, классификационные/JSON-методы — в ladder-профиль сервиса (`service:classify` по умолчанию, с переопределением через конфиг окружения), без pin конкретной модели.
- Нет D1/Vectorize/AI-биндинга: методы stateless, состояние выводится из переданного входа каждый раз. База понадобится только когда появится измеренная потребность в кэше — см. «Чего здесь нет и почему».

## Чего здесь нет и почему

Из ТЗ issue #6 и #10 реализовано то, что чинит реальные дефекты. Остальное отложено по замерам, а не по нежеланию:

| Из ТЗ | Статус | Почему |
|---|---|---|
| #6 §4 Обязательное состояние диалога | **сделано** | чинит реальные дефекты: переспрос отвеченного, игнор запрета контакта, выдуманное время |
| #6 §6 Валидация результата | **сделано** | guard детерминированный, 0 токенов |
| #6 §5 Embeddings (BGE-M3) + Vectorize | отложено | история в рекрутинге ≤ 8 сообщений ≈ 1800 токенов; векторный поиск по такому объёму дороже и менее надёжен, чем передать историю целиком |
| #6 §5 Теги + RRF + budget packing | отложено | то же: нет измеренной потребности в сжатии |
| #6 §8 30 размеченных сценариев | частично | 17 регрессионных кейсов из §8 покрыты тестами; полный корпус — отдельная задача |
| #10 §6.3 Сжатие длинного ввода | **сделано** | детерминированный отбор: первое и последнее предложение + релевантное из середины. Переписывать нельзя — инверсия отрицания меняет выбранный вариант |
| #10 §6.4 Embeddings для отбора истории | отложено | то же; все decision options всегда доходят до выбора, top-k не применяется в принципе |
| #10 §7 Workers AI как классификатор | **отклонено намеренно** | ADR-0001 запрещает собственную конфигурацию моделей и ключи. Общая лестница уже Worker; второй владелец конфигурации не появляется |
| #10 §7 Выбор модели сравнением кейсов | **сделано** | лестница выбрана замером, а не названием: `service:classify` дала 0.883 против 0.852 у `conversation` при 3 сбоях инфраструктуры вместо 5–22 |
| #10 §8 60+ размеченных кейсов | **сделано** | 100 кейсов на шести каталогах решений, включая зеркало каталога control plane; замер качества — `corpus:live`, офлайн честно не притворяется измерением модели |

Замеры (живой `llm-ladder`, 720 ч): лестница `conversations` — 1126 вызовов, 3.37M входных токенов, $1.05. Это 6.6% всех входных токенов организации, а не главный потребитель (лестница `free` — 41.5M). То есть оптимизация токенов здесь не окупает переписывание — окупает качество: переспрос отвеченного вопроса и письмо человеку, попросившему не писать, стоят дороже токенов.

## Известные ограничения (честно)

- **Перефраз не ловится всегда.** Guard сравнивает слова дословно, без лемматизации: «логистику» и «логистикой» — разные токены. Дословный повтор ловится, близкий перефраз — нет. Тест `известное ограничение: близкий перефраз ловится не всегда` фиксирует это как факт, а не прячет.
- **Состояние диалога — эвристика, не судья.** «Отвечен ли вопрос» определяется структурой (есть ли реплика после), а не смыслом. Неопределённое помечается `replied` с просьбой проверить историю, а не угадывается.
- **Сжатия нет.** Вход > 120000 символов → `INPUT_TOO_LARGE` с размерами, без молчаливого slice. Сжатие относительно цели (contract v1.1) — отдельная задача после baseline.
- **Применимость вариантов — семантика, не детерминированная проверка.** «Два применимых без приоритета → `no_matching_option`» обеспечивается схемой и промптом, а не кодом: определить применимость без модели нельзя. Качество этой границы измеряется корпусом, а не утверждается тестом.
- **Офлайн-корпус не измеряет модель.** `contract_decision_accuracy: 1` в офлайне — это утверждение о конвейере. Замер качества требует `npm run corpus:live`; в live те же величины печатаются без префикса `contract_`, чтобы их нельзя было спутать.
- **Границы интеграции, которые не лечатся в резолвере.** Control plane не передаёт `origin` (защита от инструкций в пересланном тексте на живом пути неактивна) и не сжимает историю диалога (рост контекста линеен и упирается в `INPUT_TOO_LARGE`). Обе границы зафиксированы тестами, обе — решение вызывающей стороны: [integration-v1-intent-live-acceptance.md](docs/integration-v1-intent-live-acceptance.md).
- **Полнота цели занижена методикой.** Замер 04.10.2026 на живой лестнице: `decision accuracy` 0.85, полнота `user_goal` 0.65–0.71 по строковым корням. Низкая полнота частично артефакт: модель писала «прекратить текущую задачу» вместо «остановить текущую задачу» при верном `decision`. Разделять такие случаи умеет только LLM-судья.
- **Лестница флапает.** 5–22 сбоя `502 every rung failed` из 63 кейсов в разных прогонах — это доступность воркера, не качество метода. Одиночный живой прогон невоспроизводим; для сравнения пригодны попарные прогоны без `infra_failures`.
