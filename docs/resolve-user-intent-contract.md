# resolve_user_intent — контракт второго метода (issue #10)

ТЗ: [issue #10](https://github.com/trained-assist/trained-assist-communication-skills/issues/10).
Первый метод — [spec.md](spec.md) (`generate_next_message_to_conversation_partner`).
Методы живут в одном Worker'е и говорят по одному протоколу. Публичный контракт
`resolve_user_intent` остаётся ровно `{ user_goal, decision }`. Его закрытый
список решений не используется `evaluate_next_goal`: тот формулирует открытую
следующую цель по общей цели диалога и извлечённому состоянию.

## 1. Что делает метод

Формулирует цель пользователя и выбирает **ровно один** id из закрытого списка,
переданного вызывающей стороной. Не исполняет решение, не пишет сообщение, не
запускает агента, не открывает `resource_ref`.

```
POST /v1/intents/resolve          → { "user_goal": "...", "decision": "..." }
POST /mcp  tools/call             → тот же handler, structuredContent = те же два поля
```

Встроенного списка маршрутов нет. «Ответить через LLM», «запустить OpenCode»,
«взять шаблон», «спросить уточнение» — варианты конкретного приложения, и только
если оно передало их во входном списке. Другое приложение передаёт другие варианты —
и разрешённые `decision` меняются без изменения кода метода (проверяется тестом
`замена каталога меняет enum в запросе без изменения кода` и корпусом I25/I26).

## 2. Выход ровно из двух полей

```json
{
  "user_goal": "Подобрать актуальные вакансии по резюме, не отправляя отклики",
  "decision": "start_opencode"
}
```

`user_goal` — формулировка желания пользователя: подзадачи, отрицания, ограничения,
требуемый результат, связь с текущей задачей. Не подменяется возможностями
приложения, не дополняется невыраженными действиями. Несколько просьб — общая цель
с перечислением частей внутри того же текстового поля.

`decision` — стабильный id одного переданного варианта либо зарезервированное
`no_matching_option`. Свои варианты модель не придумывает.

**Дополнительных полей в успешном JSON нет**: ни `route`, `ни `intent.kind`,
`confidence`, `reply_plan`, `handoff`, `reason`, `status`. Диагностика живёт в
транспортном контексте:

| Дверь | Где диагностика |
|---|---|
| MCP | `CallToolResult._meta`: `request_id`, `trace_id`, `bundle{id,version}`, `language`, `decision`, `reserved`, `generation`, `usage`, `timing`, `input_metrics`, `warnings` |
| REST | заголовки `x-communication-request-id` и `x-communication-diagnostics` (тот же объект) |

Причина именно такая: вызывающая сторона парсит `structuredContent` и не должна
иметь возможности случайно зависеть от диагностического поля. Версия пакета
возвращается в диагностике — это то, что делает устаревший результат обнаружимым
вместо молчаливого применения (§5 ТЗ).

## 3. Входной контракт

Обязательны `input_bundle`, `recipient`, `decision_options`.

```json
{
  "schema_version": "1",
  "request_id": "r-123",
  "trace_id": "trace-123",
  "input_bundle": {
    "id": "b-42",
    "version": "v1",
    "events": [
      {"id": "e1", "type": "text", "author": "user", "text": "Посмотри резюме и подбери вакансии. Пока не откликайся."}
    ],
    "attachments": [
      {"id": "a1", "name": "resume.pdf", "mime_type": "application/pdf", "resource_ref": "artifact:resume-42", "content_status": "metadata_only"}
    ]
  },
  "recipient": {"role": "Карьерный помощник", "persona": "Помогаю анализировать опыт и искать работу"},
  "decision_options": [
    {"id": "quick_llm_reply", "description": "Сформулировать ответ на основе доступного контекста без внешних действий и поиска актуальных данных", "applicability": "Объяснения, вопросы о возможностях, обсуждение предоставленных фактов"},
    {"id": "start_opencode", "description": "Запустить OpenCode для выполнения пользовательской задачи", "applicability": "Нужны внешние инструменты, поиск актуальных данных, создание артефактов или выполнение действий"}
  ],
  "decision_priority": ["start_opencode", "quick_llm_reply"],
  "capabilities": [{"id": "job-search", "title": "Поиск вакансий", "description": "Поиск актуальных вакансий по опыту и условиям", "availability": "enabled"}],
  "dialog_context": {"history": [], "active_tasks": []},
  "runtime_facts": [{"key": "run_status", "value": "завершён", "as_of": "2026-10-04T10:00:00+03:00"}],
  "source_refs": [],
  "options": {"language": "ru"},
  "model_profile": "default"
}
```

| Поле | Обязательно | Правила |
|---|---|---|
| `input_bundle.id` | да | непустая строка; возвращается в диагностике |
| `input_bundle.version` | нет | если задан — возвращается; меняется при любом изменении пакета |
| `input_bundle.events[]` | да* | `id` уникален, `type`/`author`/`text` непустые; `origin` ∈ `user_command`\|`forwarded_content`\|`document_content` |
| `input_bundle.attachments[]` | нет | `id` не совпадает с id события; `content_status` ∈ `text_available`\|`ocr_available`\|`transcript_available`\|`metadata_only`\|`unavailable` |
| `recipient.role` | да | непустая строка |
| `decision_options[]` | да | **непустой** список; `id` уникален, непуст, не `no_matching_option`; `description` содержательная (≥12 симв., не повторяет id); `applicability` опционально |
| `decision_priority[]` | нет | каждый id обязан быть в `decision_options`; `no_matching_option` не может иметь приоритета |
| `capabilities[]` | нет | помогает интерпретировать запрос, **не заменяет** `decision_options` |
| `dialog_context` | нет | `history[]` и `active_tasks[]` — для «да», «продолжай», «а это?» |
| `runtime_facts[]` | нет | единственный допустимый источник live-фактов; каждый с `as_of` |
| `source_refs[]` | нет | не открываются автоматически |
| `options.language` | нет | если не задан — определяется по письму пользовательского текста |
| `model_profile` | нет | только серверный allowlist (`default`) |

\* события могут быть пустыми, если есть вложения; пакет без того и другого —
`VALIDATION_ERROR` («цель выводить не из чего»).

### Вложения: манифест ≠ содержимое

`content_status` говорит, что реально доступно. Текст, переданный в пакете,
считается прочитанным. Статус `text_available` **без** текста считается
непрочитанным и даёт `warnings[].code = attachment_text_declared_missing` —
молчаливая потеря хуже честной пометки.

### Приоритет

`decision_priority` разрешает неоднозначность **между применимыми** вариантами и не
делает неприменимый подходящим. Порядок массива `decision_options` приоритетом не
является. Без `decision_priority` неоднозначность → `no_matching_option`.

## 4. Ни один вариант не подходит

`no_matching_option` — нормальный семантический исход, а не ошибка. Возвращается,
когда варианты не покрывают цель, не хватает существенных данных или между
применимыми вариантами остаётся неоднозначность. Если цель неизвестна, `user_goal`
выражает неопределённость прямо, а не выдуманной уверенной целью.

Повторных вызовов лестницы для `no_matching_option` нет: это ответ, а не отказ.

Технические ошибки — отдельно и никогда не маскируются под `no_matching_option`:

| Код | HTTP | Когда |
|---|---|---|
| `VALIDATION_ERROR` | 400 | вход не проходит контракт |
| `INPUT_TOO_LARGE` | 400 | вход > 120000 символов, с размерами |
| `TOO_MANY_DECISION_OPTIONS` | 400 | > 32 варианта или > 24000 символов описаний — варианты не выбрасываются молча |
| `MODEL_PROFILE_NOT_ALLOWED` | 400 | `model_profile` вне allowlist |
| `LLM_UNAVAILABLE` | 503 | лестница недоступна / таймаут / сеть |
| `INTENT_REJECTED` | 422 | guard отклонил ответ на всех попытках |
| `INTERNAL` | 500 | непредвиденное |

## 5. Guard (детерминированный, 0 токенов)

| Проверка | Вердикт | Зачем |
|---|---|---|
| Ровно два поля, `decision` ∈ enum, `user_goal` ≥ 10 симв. | `shape_invalid` | контракт ответа |
| `user_goal` дословно повторяет описание варианта | `goal_is_option` | «Не подменять желание предполагаемыми возможностями приложения» |
| `user_goal` называет время/дату, которых нет во входе и в `runtime_facts` | `invented_time` | live-факты задаёт вызывающая сторона, а не модель |
| `user_goal` утверждает содержимое вложения без текста | `unavailable_source` | «Файл только с manifest позволяет понять "переведи PDF", но не позволяет отвечать о его содержании» |

При отклонении — **одна** ремонтная попытка с объяснением, ЧТО не так (иначе модель
повторяет ту же ошибку и бюджет сгорает впустую). Общий бюджет метода: 2 вызова
лестницы, и он не перемножается с внутренними retry лестницы.

Чего guard **не** проверяет и не должен: применимы ли два варианта одновременно.
Это семантика, она остаётся за классификатором и измеряется корпусом.

## 6. Модель и лестница

| Роль | Лестница | Профиль | Почему |
|---|---|---|---|
| классификатор | **`service:classify`** (общая) | `temperature: 0`, `max_tokens: 400` | резолвер не пишет текст человеку — он выбирает id из закрытого списка. Это классификация, и лестница под неё настроена: free-first, все ранг-и бесплатные |

`conversation` — лестница writer'а: там нужен живой ответ и качество формулировки.
Резолверу она была назначена по инерции первого метода, и это стоило 19 % отказов
на 24 ч (см. ниже). Решение владельца 17.10.2026.

`LLM_LADDER_NAME` переопределяет имя — это и есть «выбрать модель сравнением
размеченных кейсов» (§7). В проде без флага.

### Почему не `conversation`: измерено, а не предположено

`conversation` начинается с двух платных ранг-ов OpenRouter, где осознанно
ло��ится `HTTP 402 Insufficient credits` (кредитов нет, сбой нужен, чтобы это было
видно). На 24 ч:

| лестница | вызовов | сбоев | % |
|---|---:|---:|---:|
| `conversation` | 433 | 82 | **18.9** |
| `build` | 9923 | 554 | 5.6 |
| `service` | 4203 | 120 | 2.9 |
| `free` | 12353 | 123 | 1.0 |
| `service:classify` | 225 | 0 | **0.0** |

### А что с качеством — проверено корпусом, а не решено по названию

63 оцениваемых кейса на живой лестнице. `service:classify` после двух правок
промпта оказался не просто не хуже, а лучше:

| Метрика | `conversation` | `service:classify` |
|---|---:|---:|
| decision accuracy | 0.852 | **0.883** (на отобранной выборке 0.955) |
| полнота `user_goal` | 0.653 | **0.790** |
| доля `no_matching_option` | 0.370 | 0.267 (метки ждут ~0.25) |
| потерянных ограничений | 26 | **13** |
| инфраструктурных сбоев | 5–22 | **3** |
| p50 / p95, мс | 6 436 / 20 228 | **3 561 / 16 820** |

Первый прогон на `classify` дал 0.767 — хуже. Разбор: **12 из 14 ошибок выбора
были ложными отказами** («нужно уточнить», «не хватает данных», непрочитанный
файл). Промпт дополнен двумя правилами («не выдумывай затруднения», «непрочитанный
файл не повод отказаться») — после этого 0.883.

Первая из правок расплатилась границей live-фактов: вопрос о состоянии без
`runtime_facts` стал получать вариант вместо `no_matching_option`. Правило уточнено
явным исключением, нарушений снова 0. Обе правки — результат измерения, а не
интуиции; вторая откатывает первую там, где она переусердствовала.

Схема ответа строится **на каждый запрос** из переданных ids:
`{type: object, additionalProperties: false, required: [user_goal, decision],
properties: {user_goal: {type: string, minLength: 10}, decision: {type: string,
enum: [...ids, no_matching_option]}}}` и уходит в `response_format:
{type: json_schema, json_schema: {name: intent_resolution, strict: true, schema}}`.

Валидация после вызова обязательна даже с provider JSON Schema: лестница сама
снимает `response_format` при 400 от провайдера и повторяет тот же rung без него —
схема это запрос, а не причина терять вызов. Поэтому схема дополнительно
воспроизведена в промпте, и ответ всё равно проверяется локально.

**Почему не Workers AI.** ТЗ §7 предлагает выбрать небольшую модель Workers AI для
классификатора. Не делаем: ADR-0001 запрещает собственную конфигурацию моделей и
ключи — это дублирование, которое потом никто не обслуживает. Общая лестница уже
является Worker'ом, путь запроса остаётся Worker→Worker, и второй владелец
конфигурации не появляется. Замена — осознанное отклонение от ТЗ, а не упущение.

## 7. Чего здесь нет и почему

| Из ТЗ #10 | Статус | Почему |
|---|---|---|
| §6.3 Сжатие длинного ввода | **сделано** (без LLM) | `src/intent-compress.mjs`: первое и последнее предложение + релевантное из середины, детерминированно. Переписывать текст нельзя — инверсия «пока не отправляй» меняет выбранный вариант на противоположный, поэтому предложения ОТБИРАЮТСЯ |
| §6.4 Embeddings (BGE-M3) + Vectorize для отбора истории | отложено | векторный поиск по малому объёму дороже и менее надёжен, чем передать историю целиком. Все decision options всегда доходят до выбора — top-k не применяется в принципе |
| §7 Собственный OCR/парсер всех форматов | не делается | содержимое приходит от вызывающей стороны (`text` в манифесте или через её resolver). Универсальный парсер бинарных форматов — отдельная задача вне v1 |
| §7 Кэш решения | не делается | stateless-контракт: состояние выводится из переданного входа каждый раз. Кэш понадобится при измеренной потребности |

## 7a. Сжатие длинного ввода

`src/intent-compress.mjs`. Порог — 12000 символов на событие (~4800 токенов
русского); ниже порога вход идёт целиком, «не запускать сжатие ради формальности»
не требуется. Целевой бюджет после сжатия — 2000 символов.

| Правило | Что сохраняет |
|---|---|
| всегда | первое и последнее предложение |
| `negation` | «не», «пока не», «без», «кроме», «запрещено», «нельзя», «сначала», «только лишь» |
| `command` | глагол-команда: «найди», «подбери», «переведи», «запусти», «сформируй», «удали»… |
| `question` | вопрос о факте или возможности |
| `fact` | число, дата, деньги |
| `source` | файл, документ, резюме, картинка, лог |

Три свойства, которые здесь принципиальны:

1. **Отбор, а не пересказ.** Модель в сжатии не участвует. Единственное, что здесь
   недопустимо, — инверсия отрицания, а отбор предложений изменить смысл не может.
2. **Порядок жертв по цене ошибки**, а не по расстоянию до края:
   `fact → question → source → command → negation`. Первая версия резала по
   расстоянию и первой выбрасывала предпоследнее предложение — то есть ровно то,
   где обычно стоит «пока не отправляй». Отрицание терялось; это нашли живые
   прогоны, а не рассуждение.
3. **Релевантность синтаксическая, не по близости к capabilities.** «Найди курсы
   по английскому» не похож ни на одну capability — и не должен отбрасываться
   (ТЗ §6.3 прямо это запрещает).

Молчаливого сжатия нет: в `_meta.warnings` приходит `input_compressed` с
соотношением предложений и символов до/после и разбивкой потерь на
`dropped_by_rules` и `dropped_by_budget`. Только счётчики и id события — текст
выброшенных предложений в диагностику не попадает. Вложения не сжимаются: манифест
не текст.

Для замера «полный контекст против сжатия» (§9) есть `INTENT_COMPRESS=off` — он
не для прод, а чтобы сравнение было честным.

## 8. Покрытие входа

`input_metrics.coverage` сообщает честно: сколько событий, вложений и вариантов
дошло до классификатора. Сейчас это всегда `N из N` и `truncated: false` — не
потому что так удобно писать, а потому что отбрасывать нечего: всё передаётся
целиком, а переполнение даёт явную ошибку. Если появится блочный проход, этот
же отчёт покажет неполный проход вместо того, чтобы выдать его за полный.

## 8a. Живой замер 04.10.2026 (лестница `conversation`, 63 оцениваемых кейса)

Замер выполнен после нахождения токена (см. `trained-assist-agent` → `docs/llm-ladder-token.md`).

| Метрика | Полный контекст | Со сжатием |
|---|---:|---:|
| decision accuracy | 0.852 | 0.845 |
| полнота `user_goal` (строковые корни) | 0.653 | 0.707 |
| доля `no_matching_option` | 0.370 | 0.345 |
| потерянных размеченных ограничений | 26 | 22 |
| входных токенов | 87 167 | 76 273 |
| p50 / p95, мс | 6 436 / 20 228 | 6 417 / 20 223 |

**Попарное сравнение тех же кейсов** (38 сопоставимых, 25 отпали из-за сбоев лестницы):
одинаковый вердикт — **34 (89,5 %)**, разный — 4, из них:

- **3 различия — шум модели, а не влияние сжатия.** `I04`, `N03`, `N06` — короткие
  входы, сжатие на них не срабатывает вовсе, модель просто ответила иначе при
  втором прогоне;
- **1 различие — настоящее**, и его нашёл именно этот замер: на `C03` («удали мою
  подписку», 22k символов болтовни, варианта удаления в каталоге нет) модель вместо
  `no_matching_option` выбрала `start_opencode` — то есть ровно то, что ТЗ запрещает
  («метод не превращает отмену в запуск нового OpenCode»). Промпт дополнен двумя
  правилами («не выбирай ближайший вариант», «болтовня без просьбы — не задача»), после
  чего `C03` зелёный.

Вывод по сжатию: **на живых данных оно не ухудшило выбор варианта** — 3 различия из 4
приходятся на кейсы, где сжатие не работает, а единственное реальное различие
исправлено точечной правкой промпта. Экономия ~12 % входных токенов. Это не
доказательство «сжатие безопасно всегда»: выборка — 63 кейса, модель стохастична,
и один замер не отделяет сигнал от шума.

### Что замер честно НЕ доказал

- **Полнота цели занижена методикой.** Проверка строковыми корнями требует, чтобы
  модель упомянула смысловой корень; на кейсах вроде «остановить текущую задачу» она
  писала «прекратить текущую задачу», и `decision` при этом была верной. 0.65–0.71 —
  это нижняя оценка, а не «модель теряет треть ограничений». Разделять эти два случая
  умеет только LLM-судья, а он в бюджете метода не предусмотрен.
- **Доступность лестницы.** 5–22 сбоя `HTTP 502 every rung failed` из 63 в разные
  прогоны. Они вынесены в `infra_failures` и не считаются провалом кейса, но делают
  одиночный прогон невоспроизводимым: для сравнения пригодны только попарные прогоны
  без инфраструктурных сбоев.
- **Числовая уверенность модели не измерялась** и не выдаётся за вероятность: в
  контракте поля `confidence` нет.

## 10. Запуск и проверка

```bash
npm ci
npm run gate          # check + 156 тестов + песочница 35/35
npm run corpus        # 72 размеченных кейса, офлайн (лестница подменена скриптом)
npm run corpus:live   # то же против живой лестницы: нужны LLM_LADDER_URL/LLM_LADDER_TOKEN
npm run dev           # wrangler dev на :8787
```

Живой прогон на workerd (проверено 04.10.2026): `/health` → `ready`, REST
`/v1/intents/resolve` → 200 с двумя полями и диагностикой в заголовках, MCP
`tools/list` → список инструментов, `tools/call resolve_user_intent` → `structuredContent`
с двумя полями и `_meta`. Секреты организации не нужны: лестница подменяется локально.

**Чего офлайн-проверки не доказывает.** Что модель выбирает правильный вариант.
Офлайн-прогон подменяет лестницу скриптом, поэтому `contract_decision_accuracy: 1`
— утверждение о конвейере, а не о качестве. Замер качества — только
`npm run corpus:live`, и раннер печатает это предупреждение сам, чтобы зелёный
офлайн-прогон нельзя было выдать за измерение модели.
