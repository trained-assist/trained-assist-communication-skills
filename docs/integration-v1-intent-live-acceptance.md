# Integration v1 — приёмка качества входного решения `resolve_user_intent`

Как потребитель (control plane, PR #43) проверяет, что перефразирования, составные
запросы и продолжения диалога маршрутизируются правильно. Один воспроизводимый
запуск, чтение результата, ожидаемые границы.

Связанные документы: [resolve-user-intent-contract.md](resolve-user-intent-contract.md) ·
[requirements-log.md](requirements-log.md) · архитектурный пункт приёмки
[trained-agent-architecture#140](https://github.com/trained-assist/trained-agent-architecture/issues/140).

## Что здесь измеряется, а что — нет

| Слой | Чем меряется | Что доказывает |
|---|---|---|
| контракт и детерминированные слои | `npm run gate`, `npm run corpus` (офлайн) | вход валиден, guard ловится, промпт доезжает, ограничения не теряются |
| **качество выбора модели** | `npm run corpus:live -- --catalog integration-v1` | `decision` совпадает с меткой, `user_goal` полон, latency, токены |

Офлайн-прогон подменяет лестницу скриптом, который отвечает размеченным ответом.
Поэтому `contract_decision_accuracy: 1` в офлайне — утверждение о конвейере, а не о
модели. В live-режиме те же величины печатаются без префикса `contract_`
(`decision_accuracy`, `goal_completeness`, `lost_constraints`), чтобы одно нельзя
было выдать за другое.

## Каталог `integration-v1` — зеркало вызова control plane

`scripts/corpus/cases.json`, `catalogs.integration-v1` — копия того, что реально
отправляет CP #43 (`src/router/communication-v1.ts`): `system_health` +
`catalog.brief` + `agent`, строки и `applicability` скопированы дословно.
`decision_priority` CP не передаёт, поэтому и в каталоге его нет: «два применимых
варианта» здесь неоднозначны по определению.

Отличия живой формы от корпуса, которые важно понимать до чтения результатов:

- **вложения всегда без текста.** CP отправляет `{id, name, resource_ref, content_status:'metadata_only'}`,
  поэтому «прочитать нечего» — основной, а не редкий случай;
- **`origin` не передаётся ни для одного события.** Пересланный текст попадает в
  раздел «Команда пользователя» вместе с настоящей командой (см. «Границы» ниже);
- **`runtime_facts` и `source_refs` не передаются**; `options.language` — всегда `ru`;
- **любая ошибка resolver'а деградирует в `agent`.** `no_matching_option`, неизвестный
  id, `INTENT_REJECTED`, таймаут — для CP это один исход: `degraded: true`,
  `COMMUNICATION_FALLBACK`, уведомление пользователю «Определение маршрута недоступно».
  Поэтому цена ошибки выбора — не потеря задачи, а **потеря быстрого ответа**:
  `system_health`/`catalog.brief` вместо `agent` (пользователь получает статический
  каталог вместо работы) и лишняя платная попытка лестницы.

## Один запуск

```bash
# секреты общей лестницы — из окружения интегратора, в репозиторий не попадают
LLM_LADDER_URL=...  LLM_LADDER_TOKEN=... \
  node scripts/corpus/run.mjs --live --catalog integration-v1 --verbose
```

Прогон **read-only**: он обращается только к общей лестнице (`service:classify`).
Ничего не деплоит, не меняет bindings, не пишет в control plane, не трогает
Telegram. Стоимость одного прогона — порядка 22k входных + 1k выходных токенов на
25 кейсов при подставном ответе; живые ответы длиннее.

Ожидаемый выход: 25 кейсов, из них 1 помечен `ladder_calls: 1` и 24 уходят в лестницу
один раз. `skipped_offline_only: 0` — на этом каталоге нет кейсов с подсованным
guard'у дефектом.

## Что читать в отчёте

| Метрика | Что означает | Красный признак |
|---|---|---|
| `decision_accuracy` | доля кейсов, где `decision` попал в `accepts` | ниже 0.9 на 25 кейсах = разбирать каждый красный |
| `false_fast` + `false_fast_cases` | быстрый вариант выбран там, где задача должна была уйти в `agent` (V06–V08) | **любое ненулевое значение** — самый дорогой класс: задача теряется молча |
| `lost_constraints` | сколько размеченных ограничений не попало в `user_goal` | ненулевое на V12–V14, V24 = потеряно «не отправляй»/«не меняй» |
| `goal_completeness` | доля проверок `goal_contains`, попавших в цель | заметное падение обычно означает переформулировку, а не потерю; читать кейсы |
| `no_matching_share` | доля `no_matching_option` | для CP безопасно (идёт в `agent`), но рост означает ложные отказы |
| `live_state_violations` | V19: ответ про состояние мира без `runtime_facts` не `no_matching_option` | ненулевое = выдуманный факт |
| `p50_ms` / `p95_ms` | задержка метода целиком | p95 выше таймаута вызывающей стороны (70 c CP) = метод не укладывается |
| `total_input_tokens` / `total_output_tokens` | usage от лестницы | вход растёт с `history_chars`: контекст не сжимается |
| `infra_failures` / `infra_codes` | технические сбои лестницы | выпадают из знаменателя accuracy; сравнивать прогоны только при нуле |

Одиночный живой прогон **невоспроизводим** по качеству: лестница флапает
(5–22 сбоя `502 every rung failed` на 63 кейса в разных прогонах). Для сравнения
нужны попарные прогоны; один прогон годится только чтобы увидеть конкретные красные
кейсы.

## Воспроизведённые дефекты, уже исправленные в этом PR

Каждый воспроизведён на реальном обработчике и закрыт регрессией; в `--live` эти
кейсы больше не падают в `INTENT_REJECTED`.

| # | Дефект | Симптом | Где чинится |
|---|---|---|---|
| 1 | `dialog_context.active_tasks` не входил в подтверждённые источники | «продолжай» после задачи, в цели которой есть дата → `INTENT_REJECTED`, 2 платных вызова, деградация маршрута | `src/intent-guard.mjs` |
| 2 | «прочитать нечего» считалось утверждением о содержимом | честный ответ о непрочитанном вложении → `INTENT_REJECTED` (2 вызова) вместо решения | `src/intent-guard.mjs` |
| 3 | длинное несжимаемое событие уходило к лестнице молча | 48k символов целиком при `events_compressed: 0` и без warning; метрика утверждала «вход уместился» | `src/intent-compress.mjs` |

## Границы, которые этот PR не меняет

Их зафиксировали тесты, чтобы изменить нельзя было молча. Ни одна не лечится в
resolver'е: все три — решения вызывающей стороны или его политики.

1. **`origin` не передаётся.** Resolver различает команду и присланный текст, но CP
   не заполняет поле, поэтому на живом пути инструкция внутри пересланного текста
   попадает в раздел команд. Защита работает в `V21` (с `origin`) и не работает в
   `V22` (ровно как отправляет CP). **Зависимость от CP, не дефект resolver'а.**
2. **История диалога не сжимается.** Сжатие трогает только `input_bundle.events`.
   `durableContext` CP отдаёт все соседние задачи вместе с `result_json`, поэтому
   рост контекста линеен: 40 задач ≈ 36k символов (нормально), 200 задач ≈ 180k →
   `INPUT_TOO_LARGE` → деградация маршрута **на каждый** последующий запрос в этом
   диалоге. Прямо бьёт по пункту приёмки «продолжение по месяцам». Место решения —
   обрезка истории в CP или другой лимит; здесь это было бы расширением контракта.
3. **Применимость варианта — семантика.** «Составной запрос не превратился в быстрый
   ответ» детерминированно не проверяется: разница между «что ты умеешь?» и «что ты
   умеешь? и посчитай расходы» смысловая. Её место — `false_fast` в живом прогоне,
   а не assert в коде.
