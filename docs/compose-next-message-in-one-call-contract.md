# compose_next_message_in_one_call — контракт (issue #28)

## Зачем этот метод

Подготовка ответа кандидату сейчас строится как цепочка отдельных вызовов:
`extract_conversation_state` → `evaluate_next_goal` → `generate_next_message`. Для обычного
продолжения это три вызова общей лестницы там, где содержания хватает на один.

`compose_next_message_in_one_call` — эксперимент рядом с цепочкой, а не её замена:

```text
диалог + цель диалога + ограничения -> {key_facts, next_goal, message} за ОДИН вызов
```

**Существующая цепочка остаётся эталоном и fallback'ом.** Метод не становится production
default: потребитель выбирает его явно (`fallback` плюс отдельный маршрут), пока владелец не
рассмотрел качество и trade-off из [бенчмарка](scripts/benchmark/report.md).

Связанные задачи: [эпик трёхшагового контракта #11](https://github.com/trained-assist/trained-assist-communication-skills/issues/11),
[ревью задержки, токенов и preflight #23](https://github.com/trained-assist/trained-assist-communication-skills/issues/23).

## Вход

Обязательные поля:

| Поле | Что это |
|---|---|
| `conversation_objective` | Верхнеуровневая цель диалога. Из неё метод сам формулирует цель следующего шага — отдельного `goal` не требуется. |
| `communication_style` | Только голос, тон, обращение, степень формальности. |
| `language` | Явный код языка сообщения (`ru`, `en`). |
| `conversation_history` | Tagged union `{format:"messages",…}` или `{format:"text",…}` — как у writer'а. |

Необязательные: `partner_profile`, `sender_profile`, `context`, `constraints`, `request_id`,
`trace_id`, `context_revision`, `model_profile`, `material_bindings`, `fallback`.

Общий вход ограничен 120000 символами; превышение → `INPUT_TOO_LARGE` с размерами, без
молчаливого slice.

### `goal` и `fallback`

`goal` — единственное поле, которое **сам compose не использует**. Оно принимается, потому что
внутренний fallback запускает writer'а, а writer требует goal. Без него вызовы `compose`
остаются полностью работоспособны, но автоматический fallback невозможен: технический сбой
даст типизированную ошибку, а не результат цепочки.

`fallback`:

| Значение | Что делает технический сбой |
|---|---|
| `chain` (по умолчанию) | Запускает существующую цепочку и возвращает ЕЁ результат с пометкой в диагностике. |
| `off` | Возвращает типизированную ошибку (`COMPOSE_REJECTED` / `LLM_UNAVAILABLE`). |

## Выход

```json
{
  "status": "ready",
  "key_facts": [
    { "fact": "Кандидат подтвердил готовность выполнить тестовое",
      "evidence": { "quote": "Да, готов выполнить тестовое задание.", "message_id": "m2" } }
  ],
  "next_goal": {
    "instruction": "Уточнить объём продаж и количество карточек",
    "required_points": [],
    "forbidden_points": []
  },
  "message": { "text": "Уточните, пожалуйста, объём продаж.", "language": "ru" },
  "warnings": []
}
```

Плюс диагностика (не часть контракта): `request_id`, `context_revision`, `generation`,
`usage`, `timing`, `input_metrics`, `dialog_state`.

### Семантика статусов

| Статус | Кто ставит | `message` | Что делает потребитель |
|---|---|---|---|
| `ready` | модель | текст | Пройти свои проверки свежести/дублей/запрета контакта и решить, отправлять ли. |
| `wait` | модель | `null` | Ничего не отправлять: ждём обещанного ответа, реакции на задание или решения собеседника. Причина — в `warnings`. |
| `cannot_compose` | модель | `null` | Обоснованного сообщения не получилось. Можно запустить цепочку — на усмотрение потребителя, автоматически этого не делается. |
| `do_not_contact` | **сервер** | `null` | Не писать. Лестница при этом **не вызывается вообще**. |

`do_not_contact` — серверный статус, модель его не возвращает и не видит в схеме. Он
определяется детерминированно из полной истории до вызова лестницы, ровно как в
`evaluate_next_goal`. Метод не принимает решение об обходе запретов: он их не обходит.

### Правило `message=null`

`message` и `next_goal` обязаны быть `null` при любом статусе, кроме `ready`, и обязаны быть
непустыми при `ready`. Черновик, приложенный к `wait`, — не подсказка, а противоречие: у
`wait` и «отправить это» разные исходы, и потребитель обязан различать их без догадок.

## Evidence: цитаты только из переданного

`evidence.quote` обязан быть **дословным** фрагментом того, что вызывающая сторона реально
прислала: текста истории, `context`, профилей, ограничений или цели диалога. Перефраз,
составленная цитата и цитата из памяти модели — не evidence. Это единственное, что потребитель
не может перепроверить, не перечитав весь диалог, поэтому проверка строгая, а не «похоже на
цитату».

`evidence.message_id` допустим **только если** во входе у сообщений есть `id`; тогда цитата
обязана дословно совпадать именно с этим сообщением. Если id не переданы, поле запрещено, а
не просто необязательно: модель не должна придумывать идентификаторы, которых нет на руках.

Проверка выполняется на сервере, стоит 0 токенов, и её провал — обычная ремонтная попытка, а не
тихая потеря факта.

## Валидация

Ответ всегда проходит серверную проверку до того, как попасть к потребителю. `response_format`
с JSON Schema отправляется провайдеру, но **не считается гарантией**: ответ парсится и
проверяется локально.

Проверяются: точный набор полей, enum статуса, непустая инструкция цели от 8 символов, строковые
массивы `required_points` / `forbidden_points`, лимиты (`key_facts` ≤ 20, факт ≤ 200, цитата ≤
300, текст ≤ 4000), дословность цитат, соответствие `message.language` запрошенному языку, и
детерминированный guard writer'а (запрещённые утверждения, `max_characters`, `max_questions`,
обязательные дословные блоки, повтор, переспрос решённого вопроса, выдуманное время, язык).

Одна ремонтная попытка; при отклонении модель получает **причину**, а не тот же промпт. Общий
бюджет метода — 2 вызова лестницы, как у остальных методов.

Невалидный JSON, неверный enum и недословная цитата **никогда** не выдаются потребителю как
готовый черновик: это `COMPOSE_REJECTED` (или fallback).

## Fallback и наблюдаемость

Технический сбой (лестница недоступна, таймаут, бюджет исчерпан, ответ не прошёл валидацию за
две попытки) запускает существующую цепочку. Ошибка не превращается в пустой или выдуманный
текст.

Fallback наблюдаем и не замаскирован под обычный ответ:

- результат — это результат **writer'а** (`status: "generated"`, `message_text`), с его формой и его версией контракта; REST-ответ несёт `x-contract-version: v1` (writer), а не compose;
- `_meta.fallback = {used: true, reason, composed_attempts}` — MCP; `x-communication-diagnostics` — REST. `reason` — фиксированный ASCII-код (`ladder_unavailable`, `validation_exhausted`), а не сырой текст лестницы: диагностика едет в HTTP-заголовке, и кириллица там ломает весь ответ;
- в телеметрии виден отдельный `evt: compose` со статусом, а не `generated`.

Fallback **не** срабатывает на:

- невалидный вход — цепочка отвергла бы ту же историю, тратить бюджет незачем;
- `wait` и `cannot_compose` — это не сбой, а честный ответ модели. `cannot_compose` потребитель
  при желании обрабатывает сам.

Цепочка внутри fallback: `extract_conversation_state` с фиксированной внутренней схемой →
`evaluate_next_goal` → `generate_next_message`. Ревизия диалога — переданный
`context_revision`, а если его нет, ревизия, выведенная из содержимого истории: цепочка требует
непустую ревизию как guard от устаревших результатов, а случайный uuid не менялся бы никогда и
сделал бы проверку пустой.

## Чего метод не делает

- **Не отправляет.** В коде нет пути отправки; в ответе нет ни одного поля вида «отправлено».
- **Не отменяет проверки потребителя.** `ready` — это черновик, а не разрешение отправить.
  Свежесть диалога, дубли и повторный запрет контакта остаются у вызывающей стороны.
- **Не выбирает шаг процесса** и не меняет порядок найма.
- **Не удаляет и не переписывает** три существующих метода.
- **Не выдумывает факты, время, условия и договорённости** — ни в `key_facts`, ни в тексте.

## Модель

Общая лестница, профиль `conversation` (тот же, что у writer'а: ответ — это текст сообщения),
`temperature 0.7`, `max_tokens 1200` — больше, чем у writer'а, потому что ответ несёт
состояние, цель и текст. Конкретная модель не закреплена (ADR-0001); `reasoningEffort` не
задаётся.

Сравнение с лестницей в режиме live — только через `npm run benchmark:live` с секретами общей
лестницы. Офлайн-прогон измеряет конвейер, а не модель.

## REST и MCP

```text
POST /v1/conversations/compose
POST /mcp tools/call compose_next_message_in_one_call
```

Ошибки: `VALIDATION_ERROR` (400), `INPUT_TOO_LARGE` (400), `MODEL_PROFILE_NOT_ALLOWED` (400),
`LLM_UNAVAILABLE` (503), `COMPOSE_REJECTED` (422).

## Почему выбрана такая форма ответа

Issue #28 предлагал сравнить три варианта. Решение принято после прототипа:

| Вариант | Решение | Почему |
|---|---|---|
| Вложенная `state` / `goal` / `message` | **отклонён** | `state` без статуса и без правил цитат превращается в свободный текст, который потребитель всё равно не сможет проверить. Плоский `key_facts` + правило evidence делает проверку детерминированной. |
| Плоская `key_facts` / `next_goal` / `message_text` | **взят, с `message.text`** | `message` — объект, а не голая строка: язык текста должен быть в контракте, а не выводиться догадкой по алфавиту. |
| Отдельный закрытый список `action` | **отклонён** | `status` уже отвечает на вопрос «отправлять ли», а `next_goal.instruction` открыт по замыслу (как в `evaluate_next_goal`). Второй классификационный список — это второе место, где модель может ошибиться, и потребитель всё равно не может по нему действовать иначе. |

## Замер

Разметка и критерии зафиксированы ДО сравнения в `scripts/benchmark/cases.json` (12 синтетических
диалогов, персональных данных нет). Отчёт: [scripts/benchmark/report.md](scripts/benchmark/report.md).

```bash
npm run benchmark        # офлайн: конвейер, валидация, число вызовов
npm run benchmark:live   # живая лестница: p50/p95, токены, стоимость, first-pass, fallback
```

Измеряются: доля валидного результата, доля успеха с первой попытки, доля семантических ошибок,
доля fallback, p50/p95 полной задержки, входные и выходные токены, стоимость — отдельно для
простых и неоднозначных кейсов.

Честные ограничения отчёта:

- офлайн-прогон **не измеряет** задержку, токены, стоимость и качество модели — подменённая
  лестница отвечает мгновенно и отдаёт размеченный ответ;
- слепой оценки качества текста нет: она требует отдельного LLM-судьи, и оценивать два текста
  одной и той же моделью без анонимизации — это мерить собственную предвзятость;
- один живой прогон лестницы невоспроизводим (доступность воркера флапает), для сравнения
  пригодны попарные прогоны без `infra_failures`;
- выводы по задержке и токенам нужно свести с ревью #23 — это открытая работа, а не выполненная.
